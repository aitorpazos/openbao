## Scope, evidence, and interpretation

- **Snapshot:** public documentation fetched 2026-10-11; local inventory inspected on the same date. This is a census of the **current, unversioned documentation**, not every historical Vault release.
- **Enumeration:** fetched [sitemap index](https://developer.hashicorp.com/sitemap.xml), its `sitemap-0.xml` and `server-sitemap.xml` children, and **all 819 listed Vault pages in the requested trees: 190 API pages and 629 documentation pages**. Every page returned HTTP 200. Extraction used HTTPS requests and BeautifulSoup, including main-body text, headings, endpoint tables, and links. Both [API index](https://developer.hashicorp.com/vault/api-docs) and [docs index](https://developer.hashicorp.com/vault/docs) were fetched. The entire `/vault/docs/enterprise/` subtree was included.
- **Version labels:** **every one of those 819 pages displayed `v2.x (latest)`**. Thus **every source link in the tables below has the observed label `v2.x (latest)`**, including sources whose API pages omit an Enterprise badge. The version dropdown's `v1.21.x`, etc. are alternate documents, not the selected version. This rolling label is not a tested binary release. Agentic IAM pages additionally specify Enterprise **2.1.0+**.
- **Clean room:** upstream evidence came only from public `developer.hashicorp.com/vault/api-docs` and `/vault/docs` pages. No Vault source, binaries, private material, or git commands were used. Local OpenBao implementation inspection is separately identified below.
- **Inventory:** 73 YAML files with 73 `api:` entries in 17 feature directories, plus 13 existing Markdown notes. Existing specs were read, including request paths and deferred-coverage notes. Exact file/API inventory appears at the end.
- **Verdicts:** no server or conformance suite was run for this documentation-only task. **All current runtime verdicts are UNKNOWN.** A checked-in spec, route, unit test, or historical PASS is not proof of current parity. In particular, accepted 404s and missing-input 400s can pass when a feature is absent.
- **Status vocabulary:** **ALREADY COVERED** means work/specs already exist for the described subset, not complete feature parity; **PARTIAL** explicitly identifies unspecced operations or fixture gaps; **NOT COVERED** means no corresponding conformance scenario was found. **No route found** refers to the inspected `internal/vault` surface, not a proof that every plugin/package lacks an implementation.
- **Priority:** **High** = documented, clear operator HTTP/CRUD surface that can support focused specs; **Medium** = distributed, cryptographic, streaming, provider, or destructive fixtures dominate; **Low** = file configuration, CLI/integration guidance, or no distinct documented HTTP contract. Priorities apply to the *remaining work*, not the value of existing features.

## Executive findings

The largest mistake would be treating the existing feature-directory list as complete Enterprise coverage. Entire documented families have **no specs**: managed keys, key-management secrets engine, control groups, UI customization, licensing/usage reporting, SAML, SCEP auth, OS local accounts, PKI External CA, Enterprise PKI and Transit extensions, audit filters, and event subscriptions.

Several areas described as “done” still have concrete gaps: **seal rewrap**, **identity-based rate limiting**, **rotation orphans**, **DR operation-token management and secondary maintenance**, **Autopilot configuration**, and positive workflows in Transform/KMIP/SCIM/SPIFFE/sync/agent registry. Named Duo/Okta/PingID method configuration is already specced and implemented, but **Step-up enforcement explicitly rejects those providers**.

Start with control-group configuration/authorization, group-policy application, UI configuration, rotation-orphan listing, rate-limit grouping, and managed-key management. Add license/status and usage schemas with an explicit policy decision about compatibility versus vendor licensing. Separately schedule crypto/PKI and multi-cluster fixtures.

## 4. Negative findings and classification safeguards

1. **“Enforce session management?”** No corresponding Enterprise operator endpoint, `enforce_session` setting, or dedicated feature contract was found in the fetched API/docs corpus. Matches for “session management” concern cloud access architecture and MSSQL provider logging, not a Vault operator session-management API. This is **not an actionable endpoint gap** without further public evidence.
2. **“Managed CAs” / “staged issuers?”** Managed-key PKI integration, multi-issuer rotation primitives, secure CA-key export/import, and the PKI External CA engine are documented. No independent managed-CA or staged-issuer API family was discovered. Ordinary multi-issuer support must not be reclassified as Enterprise-only.
3. **KV v2:** [API](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2) does not mark a distinct Enterprise KV CRUD family. The [subkeys cookbook](https://developer.hashicorp.com/vault/docs/secrets/kv/kv-v2/cookbook/read-subkey) puts an Enterprise badge on the **GUI** instructions; CLI/API subkeys are not thereby proven Enterprise-only. Enterprise-adjacent KV behavior belongs under events, replication, sync, import and snapshot recovery.
4. **Product-name false positives:** [GitHub auth](https://developer.hashicorp.com/vault/api-docs/auth/github) mentions GitHub Enterprise; [Terraform secrets](https://developer.hashicorp.com/vault/api-docs/secret/terraform) mentions Terraform Enterprise. Those strings do not establish Vault Enterprise gating. The API index/related-tools marketing mentions likewise are not endpoints. Oracle licensing/packaging and provider-specific fields require explicit feature-level classification, not blanket inclusion of every database API.
5. **Shared APIs with Enterprise fields:** mounts/auth/audit, rate limits, Raft, PKI, Transit, password policies, token tidy and counters need field/behavior-level diffs. Their entire public API is not Enterprise-only. Conversely, absence of an API-page badge does not exclude Transform, KMIP, key management, SPIFFE or SCEP: fetched overview pages establish gating.
6. **License history:** current `/system/license` only documents `/sys/license/status`, and says stored licenses are no longer supported since 1.11. Do not add historical POST/DELETE `/sys/license` contracts based on recollection.
7. **Events:** public docs establish subscriptions, not a persistent event-trigger configuration API. **Export:** documented activity/PKI/Transform export surfaces exist; a general Enterprise operator-export endpoint was not discovered.
8. **Verdict hygiene:** `raft-autosnapshot/notes.md` and `rotation-policy/notes.md` record older FEATURE_ABSENT and expected-404 PASS results; implementations now exist locally. They are historical observations, not current verdicts. Most other notes explicitly say no licensed live conformance run occurred. No synthetic API responses or invented PASS results were used here.
